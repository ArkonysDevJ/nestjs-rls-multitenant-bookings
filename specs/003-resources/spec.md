# Feature: resources

## Summary

A tenant owns bookable resources (rooms, for example). Any member can see the
active ones; only an owner can add one.

## Scenarios

### List resources — `GET /v1/resources`

Headers: `Authorization`, `x-tenant-id`.

| Given | When | Then |
|---|---|---|
| Any member of the tenant | They list | 200, the tenant's **active** resources ordered by name: `[{ "id", "name", "capacity", "active" }]` |
| The caller is not a member of `x-tenant-id` | They list | 401 |

### Create a resource — `POST /v1/resources`

Body: `{ "name": <string, 1 to 120 characters>, "capacity"?: <integer, 1 or more> }`.

| Given | When | Then |
|---|---|---|
| An owner | They create `{ "name": "Room A", "capacity": 4 }` | 201 `{ "id", "name": "Room A", "capacity": 4, "active": true }` |
| An owner, no capacity | They create `{ "name": "Room A" }` | 201 with `"capacity": null` |
| `capacity` is 0 or not an integer, `name` is empty, or the body has an unknown property | They create | 400 |
| Staff or viewer | They create | 403 |

## Requirements

- **FR-1** The tenant of a new resource comes from the request context, never
  from the body, even if the body carries a `tenant_id`.
- **FR-2** A tenant's resources are only visible to its members.
- **FR-3** The id of a resource is a UUID generated by the database.
- **FR-4** New resources are active. Only active resources are listed.

## Out of scope

Renaming, deactivating or deleting a resource, per-resource opening hours.
